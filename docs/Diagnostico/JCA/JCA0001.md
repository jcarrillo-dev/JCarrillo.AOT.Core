# Diagnóstico JCA0001: Uso de delegados Func con riesgo de allocations

| Propiedad | Valor |
| :--- | :--- |
| **Identificador** | JCA0001 |
| **Severidad por Defecto** | Warning |
| **Categoría** | Rendimiento (Performance) |
| **Módulos Afectados** | ValueLINQ (Eager y Delay) |

---

## 1. Descripción

Este diagnóstico se emite cuando se invocan los métodos de extensión ergonómicos de ValueLINQ (`Where`, `Select` y `ProcesarChunk`) utilizando expresiones lambda o delegados convencionales (`Func<T, bool>`, `Func<T, TResultado>` o `ProcesarChunkDelegado<T>`) en lugar de estructuras personalizadas que implementan las interfaces dedicadas (`IWhereDelegado<TOrigen, TDato>`, `ISelectDelegado<TOrigen, TResultado>` o `IProcesarChunkRefDelegado<T>`).

El propósito de esta advertencia es alertar al desarrollador sobre posibles **asignaciones de memoria implícitas (allocations) en el Heap de GC** en rutas de ejecución críticas de alto rendimiento.

---

## 2. Causa Técnica

En .NET, el uso de expresiones lambda tradicionales puede generar dos tipos de allocations en el Heap de GC:

1.  **Asignación del Delegado (Delegate Allocation)**: Cada vez que se crea una expresión lambda y se convierte a un tipo delegado `Func<...>`, se debe asignar memoria para almacenar la referencia al método y el contexto del destino (target).
2.  **Asignación de la Clase de Clausura (Closure/Display Class Allocation)**: Si la lambda captura variables locales del contexto que la envuelve (por ejemplo, variables declaradas fuera de la lambda), el compilador de C# genera automáticamente una clase interna (llamada *display class* o contexto de clausura) en el heap para retener los valores capturados. Esto genera aproximadamente **152 Bytes (medido)** de allocations por operación en rutas calientes.

Además, el uso de delegados introduce una **barrera de inlining** para el compilador JIT/AOT. Dado que el destino de la llamada del delegado solo se conoce en tiempo de ejecución, el compilador no puede inlinear la lógica del usuario directamente en el bucle principal, incurriendo en el costo de llamadas indirectas (`calli` a nivel de ensamblador) por cada elemento de la colección.

---

## 3. Guías de Solución y Remediación

Existen dos alternativas para resolver o mitigar este diagnóstico según el perfil de rendimiento y la legibilidad que requiera tu aplicación:

### Alternativa A: Uso de Lambdas Estáticas (`static`) — Mitigación Ergonómica
Si deseas mantener la ergonomía de la sintaxis lambda pero evitar asignaciones de memoria, puedes marcar las lambdas como **estáticas (`static`)**:

```csharp
// ❌ INCORRECTO: Causa allocations de clausura y delegado
int bitMask = 1;
using var query = array.ToValueQuery().Where(x => (x & bitMask) == 0);

//  CORRECTO: Cero allocations (0 B) en Heap
using var query = array.ToValueQuery().Where(static x => (x & 1) == 0);
```

#### ¿Por qué funciona?
Al marcar la lambda con el modificador `static`, el compilador de C# prohíbe la captura accidental de cualquier variable local. Esto permite al compilador **cachear la instancia del delegado `Func` en un campo estático interno**. Como resultado, la asignación ocurre una sola vez en el ciclo de vida de la aplicación, logrando **0 Bytes (medido)** en ejecuciones subsecuentes del bucle.

*Nota: Dado que esta alternativa sigue utilizando delegados `Func` por debajo, el compilador JIT/AOT aún no podrá aplicar optimizaciones de inlining total.*

---

### Alternativa B: Uso de Structs Dedicados — Rendimiento Máximo (Recomendado)
Para eliminar por completo tanto las asignaciones de memoria como la barrera de inlining en rutas críticas de alto rendimiento, debes definir estructuras dedicadas que implementen `IWhereDelegado` o `ISelectDelegado`:

```csharp
// 1. Definir los structs de procesamiento
private struct EvenFilter : IWhereDelegado<int, int>
{
    [MethodImpl(MethodImplOptions.AggressiveInlining)]
    public readonly bool Ejecutar(int item, int otro) => (item & 1) == 0;
}

private struct MultiplyByTwoSelector : ISelectDelegado<int, int>
{
    [MethodImpl(MethodImplOptions.AggressiveInlining)]
    public readonly int Ejecutar(int item) => item * 2;
}

// 2. Consumir utilizando structs pasados por valor (o por ref en Delay)
using var query = array.ToValueQuery()
                       .Where(0, new EvenFilter())
                       .Select<int, MultiplyByTwoSelector, int>(new MultiplyByTwoSelector());
```

#### ¿Por qué funciona?
Al pasar tipos de valor (`struct`) específicos en lugar de un tipo base `Func`, el compilador JIT/AOT realiza una **monomorfización** del método genérico. Esto le permite resolver la dirección del método `Ejecutar` en tiempo de compilación, aplicando **devirtualización e inlining total** de tu lógica directamente dentro del bucle de ValueLINQ.
* **Asignación**: Cero allocations absolutas (0 B).
* **Rendimiento**: Hasta **20 veces más rápido** bajo Native AOT debido al inlining total del compilador.

## 4. Configuración y Supresión del Diagnóstico

Si has optado por la **Alternativa A (Lambdas Estáticas)** y deseas suprimir la advertencia de compilación de forma segura, o si deseas desactivar la regla por completo en ciertas partes del proyecto, puedes utilizar los siguientes métodos:

### Opción 1: Supresión Local mediante Código (`#pragma`)
Es el enfoque recomendado para silenciar advertencias en secciones muy localizadas, como pruebas unitarias o clases específicas de benchmarks:

```csharp
#pragma warning disable JCA0001
using var query = array.ToValueQuery()
                       .Where(static x => (x & 1) == 0)
                       .Select(static x => x * 2);
#pragma warning restore JCA0001
```
*Nota: Solo es necesario deshabilitar `JCA0001` (nuestro identificador de diagnóstico de ValueLINQ).*

---

### Opción 2: Supresión a nivel de Proyecto (`.csproj`)
Si deseas silenciar el diagnóstico para todo un proyecto de forma permanente (por ejemplo, tu suite de pruebas unitarias):

```xml
<PropertyGroup>
  <!-- Agrega JCA0001 a las advertencias ignoradas -->
  <NoWarn>$(NoWarn);JCA0001</NoWarn>
</PropertyGroup>
```

---

### Opción 3: Configuración Global mediante EditorConfig (`.editorconfig`)
Para soluciones grandes, puedes controlar la severidad de `JCA0001` de forma centralizada utilizando un archivo `.editorconfig` en la raíz de tu repositorio:

```ini
[*.cs]
# Cambiar severidad a Silencioso / Desactivado
dotnet_diagnostic.JCA0001.severity = none

# O bien, elevarlo a Error si deseas prohibir estrictamente el uso de Func en producción
# dotnet_diagnostic.JCA0001.severity = error
```
